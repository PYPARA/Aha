# Aha UI 实现规则

本规则记录用户于 2026-10-19 明确要求的长期约束：以后的新功能必须按照项目已有 UI 要求实现。根目录 `AGENTS.md` 指向本文件，后续项目工作均应遵守。

## 1. 先找到既有模式

实现前查看至少一个同类页面及其公共组件。项目当前可复用的依据如下，若公共实现更新，应跟随当前实现，不能把本文件里的说明当作固定像素规范：

| 范围               | 当前依据                                                                                                       | 使用要求                                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 应用导航与路由外壳 | `apps/web/src/routes/_chat.tsx`、`components/RouteInsetSurface.tsx`、`components/RouteSurface.tsx`             | 页面接入现有外壳、侧栏、拖动区和窗口控件避让；同一层级不重复绘制背景与分隔线                                          |
| 顶栏与紧凑操作     | `components/chat/chatHeaderControls.tsx`                                                                       | 使用公共高度、间距、分隔线和 header controls；按信息层级安排页面标题、局部路径和操作                                  |
| 基础控件           | `components/ui/` 中的 Button、Input、Select、Checkbox、Menu、Dialog、Sheet、Tooltip、Toast、Empty、Skeleton 等 | 使用现有组件的 variant / size；不要在业务里手工仿制整套控件样式                                                       |
| 主题、皮肤与材质   | `apps/web/src/index.css`、`theme/`、`surfaceStyles.ts`、`aha/AppearanceProvider.tsx`、`aha/backgrounds.css`    | 使用语义 token 与公共 surface；保留背景隔离、玻璃与透明度机制，不能叠加多层涂底或硬编码业务配色                       |
| 字体与字号         | `index.css` 的 `--font-ui-family`、`--app-font-size-ui*`、`text-ui*`                                           | 界面文字跟随用户设置；代码内容使用既有等宽字体。优先使用语义字号，避免业务里固定 `text-sm` / `text-xs` 导致缩放不一致 |
| 图标与文案         | `~/lib/icons`、`useAhaTranslation`                                                                             | 跟随现有图标体系和翻译机制；图标按钮要有可访问名称                                                                    |

表中的 `components/` 路径均相对于 `apps/web/src/`。

## 2. 视觉与信息层级

- 同一操作区明确一个主操作，次要操作用次级按钮或菜单；未进入任务状态时，不常驻一长排禁用按钮。
- 间距、圆角、边框、焦点、hover、选中状态来自公共组件与 token。按钮保持公共组件规定的扁平处理。
- 使用内容、分组和留白建立层级；避免为每个区域额外套卡片、边框和阴影。
- 适配现有明暗主题、内置/自定义皮肤、背景及用户字号。设计示意中的具体颜色与尺寸不构成另起主题的授权。

## 3. 交互语义

- 分开管理导航位置、键盘焦点、资源选择和预览对象。左侧导航的激活态不应隐式成为内容区的批量选择。
- 同一内容区的文件与文件夹，应提供一致且可解释的选择规则；打开、预览、选择分别有明确动作。
- 桌面集合优先遵循单击单选、Cmd/Ctrl 加选、Shift 范围选择、空白处清空和框选等成熟操作。按页面性质决定支持范围，并提供可见的多选入口与键盘替代方式。
- 状态变化应保留浏览上下文；关闭预览不能丢失搜索、排序、滚动位置或已有选择。
- 破坏性动作、覆盖、批量元数据变更，要明确目标、影响与失败恢复；不能通过含糊文案隐式扩大操作范围。

## 4. 扩展和验收

公共组件不足时优先扩展公共能力，说明扩展理由和影响范围。业务特有的素材网格、框选矩形等可以有局部样式，但必须消费项目 token，不能重定义基础控件。

每次 UI 交付至少检查：

1. 与同类页面对照，确认外壳、标题层级、控件和字号一致。
2. 在明/暗主题和有背景的皮肤中检查可读性、背景隔离与弹层遮挡。
3. 在常用和窄窗口、放大字号下检查溢出与操作可达性。
4. 验证键盘焦点、交互名称、选择反馈，以及空、加载、错误和部分失败状态。
5. 根据改动风险运行必要验证，并区分“方案示意已验证”和“正式功能已实现”。

资源中心的目录导航与素材浏览规则见[资源中心使用说明](guides/RESOURCE_CENTER.md)，数据与兼容约束见[创作功能维护](development/CREATIVE_WORKBENCHES.md)。新功能继续遵守本文件；公共树、工作区详情面板和中性预览底板应优先复用。
