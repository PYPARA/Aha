# 精灵动作改用 GIF 生成（v3 方案）

状态：**M1、M2 已实现**（含“导出 GIF 预览”）；M3 的多动作和像素项目实测仍是方案。日期：2026-11-05（同日修订：取消精灵表生成方式，动作只用 GIF 生成）。当前行为见 [精灵动画工作台](../../guides/SPRITE_WORKFLOW.md)，维护约束见[创作功能维护](../../development/CREATIVE_WORKBENCHES.md)。

### M1 实际实现与方案的差异

- 没有升级 `workflowVersion`。所有 v2 动画方案都按 GIF 生成；新增的 `generation`（`version: 1`，可选 `segmentFrames`）只标记“手动尺寸按每帧解读”，缺少它的旧草稿手动尺寸原指整张精灵表，更新时改回跟随输出单帧。未确认的旧草稿不另建草稿，计划卡直接显示 GIF 任务，确认后提交。
- 分段改为平均分配：24 帧为 12 + 12，17 帧为 9 + 8。单帧动作不发送 GIF，计划提示至少 2 帧。
- 虚拟精灵表每行最多 8 帧（12 帧为 6×2），避免超出浏览器画布宽度；`SpriteTaskLayout` 的格子坐标随之换行。
- 候选 ID 保持为 GIF 资产 ID，`source` 为展开后的 PNG，`animationSource` 为原 GIF。GIF 展开失败时保留为失败候选，免费重新处理时再展开。资源中心导入的 GIF 同样先展开。
- 计划卡删除了布局参考图预览和合并模式选项，每个任务显示“GIF · 帧数 × 每帧尺寸 · 每帧时长 · 合成像素”；尺寸编辑器改为每帧尺寸、来源采样和每次请求帧数。M2 随后补齐了原图播放与切换、旧任务改为重新准备 GIF 方案和色键提示。
- 精灵 GIF 请求的 `complexity` 沿用方案参数，默认不发送。
- M1 实测（2026-11-05，krill `gpt-image-2.6-flare`，质量 low、复杂度 low）：插画 256 项目的 20 帧走路分两段各 10 帧，每帧请求 512×512，渠道按要求返回 10 帧 ×80ms，第二段携带上一段末两帧，两段均无问题提示，角色和落脚线保持一致，约 50 秒完成。过程文件在 `.tmp/gif-sprite-design/`。

### M2 实际实现

- “查看原图”对 GIF 候选默认播放原 GIF，可切换到展开帧，并显示帧数和总时长；静态原图不显示切换。展开失败的 GIF 只显示 GIF 本身。
- 失败的旧精灵表任务不再出现“重试失败任务”，改为“重新准备 GIF 方案”，按原动作生成新草稿，不会重发旧请求。
- 动作方案选色键背景时提示 GIF 杂边风险，不阻止提交；动作的格式固定显示为 GIF。
- 修帧编辑器直接使用每行最多 8 帧的展开图，没有另做帧条视图。
- 导出 GIF 预览：在前端用 `gifenc`（MIT）把导出帧编码为 GIF，每帧使用自己的时长和调色板，透明按 1 位处理并逐帧清除，循环动作无限循环、非循环动作只播一次；多个动作打包为 ZIP，不记录为“上次导出”。

## 1. 结论

动作生成**只用 GIF**，删除“让模型按布局图在一张精灵表上排格子”的生成方式。精灵表只作为**输入格式**保留：手工导入、资源中心“用于精灵”、旧项目候选的重新处理和修帧都要切格，这部分照旧可用。

- **生成**：每个动作段请求一个 GIF（`output_format: gif` + `frame_count` + `frame_duration_ms`）。
- **后处理和交付不变**：角色基准、共同画布、地面线、抠图、修帧、采纳、PNG 序列和图集导出照常使用。GIF 返回后先展开成“虚拟精灵表”，切片、分析、修帧编辑器和导出都复用现有代码。

原因：

1. **生成质量更好。** krill `gpt-image-2.6-flare` 同一角色 8 帧走路实测：
   - 色键溢色：透明 GIF 0px，精灵表 462px。
   - 原图中角色高度：GIF 469px，精灵表 345px。
   - 身份相似度：GIF 0.951，精灵表 0.936。
   - 落脚线稳定度（0.46%）和动作幅度相近。

   模型自己负责帧排列和切图，不再出现画到相邻格、空格有内容、看见布局线这类问题。

2. **只保留一种生成方式，流程更简单。** 布局参考图、逐格坐标提示词、行列排布和 1152×576 联动尺寸都不再需要，计划卡和技术参数也随之减少。
3. **GIF 不能直接当游戏资源。** 实测每帧最多 254 色，透明只有 0 和 255 两档，所有帧共用一个时长。游戏引擎仍然要用统一锚点、统一画布的 PNG 帧或图集，所以后处理要保留。
4. **代价：动作生成依赖渠道支持 GIF。** 不支持 GIF 或帧参数的模型和渠道将无法生成动作；角色单图不受影响。subrouter 会忽略帧数、时长和尺寸（固定约 9 帧、约 414px），所以返回的帧数必须核对。
5. **GIF 在模型内部也是一张合成表。** `帧数 × 每帧像素`受 655,360–8,294,400 的总像素预算和 3840 最长边限制。帧数越多，每帧越小，所以长动作仍要分段。

## 2. 新旧流程对比

| 环节       | 现在（精灵表）                                   | v3（GIF）                                                                |
| ---------- | ------------------------------------------------ | ------------------------------------------------------------------------ |
| 每次请求   | 一张表，最多 8 帧，联动 1152×576（4×2）          | 一个 GIF，每段默认最多 16 帧，`size` 指每帧尺寸                          |
| 参考图     | 角色外观图、对齐图、上一段末两帧、**布局参考图** | 角色外观图、对齐图、上一段末两帧；**没有布局图**                         |
| 提示词     | 逐格坐标、行列顺序、空格规则                     | 动作描述、帧数、循环、固定镜头、地面线比例、背景                         |
| 节奏       | 只在 Aha 内设置 FPS                              | 同时发送 `frame_duration_ms = round(1000 / FPS, 10ms)`，模型据此安排动作 |
| 一次多动作 | 合并模式可以一张表放多个动作                     | 每个请求只含一个动作                                                     |
| 原图检查   | 格子越界、空格有内容、布局线残留                 | 实际帧数与计划不一致、帧尺寸不一致、动画为空                             |
| 进入后处理 | 按 `SpriteTaskLayout` 切格                       | 展开为 1 行 N 列的虚拟精灵表，再按同一套 `SpriteTaskLayout` 切格         |
| 修帧、导出 | 不变                                             | 不变                                                                     |

## 3. 生成

### 每帧请求尺寸

尺寸由单帧输出规格推算，规则保存在 `spriteSizing.ts`，计划卡和请求使用同一结果：

- **插画**：
  - 每帧按输出单帧的 2 倍请求，取 16 的倍数。例如输出 256×256 时请求 512×512。
  - 处理时用面积平均缩小一半，把 GIF 的硬边还原成 2–4 级半透明边缘，弥补 1 位透明。
- **像素**：
  - 每帧取逻辑尺寸的整数倍，例如 64 逻辑时请求 256 或 320。
  - 保持最近邻采样和硬边，1 位透明正好符合像素模式。
- **合成表预算**：
  - `帧数 × 宽 × 高`低于 655,360 时，按整数倍放大每帧尺寸。例如 8 帧 × 256² = 524,288，低于下限，改为 8 帧 × 320²。
  - 高于 8,294,400 时，减少每段帧数。
  - 估算的合成表最长边超过 3840 时，同样减少每段帧数。
- **由模型决定**：`size` 发送 `auto`，切帧按实际返回尺寸计算。

### 分段

- **每段帧数**：
  - 默认 16，这是目前各渠道都能接受的上限。OpenAI 指南写 2–64，API Reference 写 2–16。
  - 可在技术参数中改为 2–64，受上面的像素预算约束。
- **怎么分**：
  - 12 帧动作一次请求完成；24 帧分成 16 + 8。
  - 后续段照旧携带上一段末两帧，提示词说明“接续上一段，不重复这两帧”。
- **不留单帧段**：`frame_count` 最少为 2，所以余数并到前一段后平分，例如 17 帧分成 9 + 8。1 帧的动作按静态图处理，不发送 GIF。

### 背景

- **透明（默认）**：
  - 发送 `background: transparent`。
  - 实测透明 GIF 没有色键溢色，硬边由插画的 2 倍超采样处理。
- **色键**：
  - 发送 `background: opaque`，提示词要求纯色背景。
  - GIF 调色板会把色键色量化，实测溢色 599px，比原精灵表更严重。计划卡对此给出提示，不阻止提交。

### 失败

- 渠道拒绝 GIF 或帧参数时，任务按失败显示渠道原因，不自动降级、换模型或重发。
- 失败卡片提示更换模型或渠道后重新准备方案。

## 4. GIF 进入后处理

### 展开为虚拟精灵表

1. **读取原始 GIF**：现在 `processCandidate` 读取 `edit` 变体，对 GIF 资源来说那只是第一帧 PNG，必须改为读取 `original`。
2. **逐帧解码**：用 sharp `animated: true` 解码为完整画布 RGBA。libvips 会按 GIF 的处置方式叠加帧，实现时用“局部更新帧”的夹具验证。
3. **拼成虚拟精灵表**：横向拼成宽 `N × 帧宽`、高为帧高的 PNG，保存为该候选的派生资源 `frames-sheet`。原 GIF 保留，用于原图查看和重新处理。
4. **生成布局**：`SpriteTaskLayout` 为 1 行 N 列，格子坐标即每帧位置，`frameIndex` 从段起始帧号递增。之后 `processSprite`、`analyzeSprite`、修帧编辑器和导出都按普通精灵表处理，不加分支。
5. **大小上限**：帧数超过单段上限，或总像素超过现有 64MP 规则时，阻止处理并提示，避免解码过大的 GIF。

### 帧数与时长核对

| 返回情况                  | 处理                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| 帧数与计划一致            | 正常处理                                                                                  |
| 帧数多于计划              | 全部展开；问题列表显示“返回 N 帧，计划 M 帧”；默认只启用前 M 帧，可在修帧“动作分组”中改选 |
| 帧数少于计划              | 全部展开并标为错误，阻止采纳；可在修帧中复用帧补齐，或重新生成该段                        |
| 每帧尺寸与请求不一致      | 只提示；比例不同时要求人工复核几何（沿用现有规则）                                        |
| GIF 每帧时长与 FPS 不一致 | 只记录作参考；动作节奏以 Aha 的 FPS 和逐帧时长为准                                        |

这些情况都不会自动重试或重复付费。

## 5. 界面

整体沿用现有动作页、计划卡和修帧编辑器。

**删除**：

- 计划卡里的布局参考图预览。
- 尺寸编辑器的行列排布和联动整表尺寸。
- 动作方案的合并模式（`combined`）选项。

**动作设置**（技术参数折叠区内）：

```
每段帧数  [16 ▾]       每帧尺寸  512×512（输出 256×256 的 2 倍）
背景      [透明 ▾]
```

**计划卡**：

```
走路 · 12 帧 · 12 FPS · 循环
1 个任务 · 12 帧 × 512×512 · 每帧 80ms · 合成约 3.1MP
参考：角色外观、对齐图
```

**候选检查**：

- 左侧“原图”直接播放原始 GIF，可切换到展开后的帧条；右侧仍是处理后的逐帧动画。
- 问题列表新增“帧数不一致”和“帧尺寸不一致”，按帧号定位。

**修帧编辑器**：

- 源图视图读取虚拟精灵表。帧数多于 8 时，帧条可横向滚动，或换行显示为接近方形的网格。这只改变显示方式，不改变格子坐标。
- 手工导入的精灵表仍按原来的网格切格。其他操作不变。

**导出**（第二阶段，可选）：新增“导出 GIF 预览”，从处理后的帧重新编码 GIF，只用于分享，不作为游戏资源。

## 6. 数据与兼容

- **新方案**：`workflowVersion` 升为 3，表示动作用 GIF 生成；分段帧数保存在 `generation.segmentFrames`。v3 方案的 `layout` 为 1 行 N 列，计划阶段按计划帧数预估，返回后按实际帧数重建。
- **旧项目（v1/v2）**：
  - 已采纳动作、候选、原图和处理版本照常查看、修帧和导出，“从原图重新处理 · 免费”照常可用。
  - 未确认的 v2 动作方案标为“需要重新准备”，打开后按 v3 生成新草稿，保留动作名称、描述、帧数、FPS、循环和参考图。
  - 失败的 v2 任务不能按原参数重试（精灵表请求已删除），失败卡片改为“重新准备方案”。
  - 合并模式的旧方案拆成每个动作一份 v3 方案。
- **任务记录**：`SpriteRun.submissionParameters` 记录 `outputFormat: gif`、`frameCount`、`frameDurationMs`，重试照原参数提交。
- **素材保护**：候选记录原 GIF 和 `frames-sheet` 两个资源 ID，都加入现有素材引用保护，常规清理不会移除。
- **工程包**：包含原 GIF 和虚拟精灵表。导入到旧版本 Aha 时只能看到虚拟精灵表，按普通处理版本使用。
- **AI 助手工具**（`apps/server/src/agentGateway/spriteTools.ts`）：
  - 去掉 `mode`（combined/separate）和“整张精灵表尺寸”的说明，改为描述每段帧数和每帧尺寸。
  - 旧参数传入时忽略并在结果中说明。

## 8. 阶段

1. **M1 生成与展开**：
   - 实现契约 v3、尺寸和分段规则、GIF 提示词、服务端提交与展开、帧数核对问题。
   - 删除精灵表生成路径，完成 v2 兼容处理。
   - 单测覆盖：尺寸预算、分段（17 帧 → 9 + 8）、展开坐标、帧数多或少、v2 方案转 v3 草稿、v2 候选仍可免费重新处理、手工导入精灵表仍可切格。
2. **M2 界面**：
   - 计划卡、动作设置、候选原图播放 GIF、修帧帧条显示、失败卡片。
   - 删除布局预览和合并模式入口。
   - 补浏览器用例，检查窄窗口和暗色主题。
3. **M3 实测**：
   - 在打包应用中通过正常计划卡，用 krill `gpt-image-2.6-flare` 制作：插画项目的走路（8 帧）、跑步（12 帧）、跳跃（16 帧，不循环）、24 帧长动作（检查分段衔接），以及像素项目的待机（8 帧）。
   - 检查落脚线、身份相似度、溢色和边缘。
   - 用 subrouter 验证帧数不一致的提示路径。

## 9. 待定问题

- 2 倍超采样让请求像素变为 4 倍。如果渠道按像素计费，费用会增加，计划卡需要显示。是否改为 1.5 倍，等 M3 对比后决定。
- 长动作分段时，GIF 段与段之间的衔接（循环首尾、末两帧接续）目前只有单段实测，需要 M3 验证。
- 删除合并模式后，同一角色多个动作的风格一致性只靠角色基准保证。如果 M3 发现动作之间差异明显，再评估是否在提示词中加入已采纳动作的帧作参考。
